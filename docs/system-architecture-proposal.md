# 商户-门店双系统架构方案

## 一、背景

我们要做两个系统：**商户管理后台**和**门店管理工作台**。这篇文档说清楚这两个系统各自做什么、数据怎么流转、权限怎么划分。

---

## 二、两个系统的定位

### 商户管理后台

给商户（老板/管理层）用的，核心能力：

- **数据看板**：查看所有门店的汇总数据（销售额、订单量、商品数等）
- **门店管理**：新建门店、配置门店基础信息
- **规则管理**：管理全公司通用的基础规则，例如商品分类、类目以及类目属性的创建与设置
- **审批中心**：审核门店自建商品的上架申请（后期规划）
- **权限管理**：给商户层级的人员开通权限

> 关键原则：商户后台**不直接操作商品、订单、营销等业务数据**，只做"看数据"、"定规则"和"管准入"。

**为什么这样定位？**

如果商户后台也能直接操作商品、订单等业务数据，就会出现两个系统同时修改同一份数据的情况。比如商户在后台改了某个商品的价格，门店运营同时也在改同一个商品的价格 — 谁的生效？这类冲突在日常操作中很难避免，排查起来也很困难。

因此我们的设计原则是：**商户后台管"面"（规则、准入、全局数据），门店工作台管"点"（具体怎么卖）**。两个系统的写入范围完全不重叠，从根本上避免数据冲突。商户通过规则管理（分类、类目、属性）和审批来实现管控，而不是直接下场改数据。

### 门店管理工作台

给门店员工（店长、运营、收银等）用的，核心能力：

- **商品管理**：创建商品、编辑商品、上下架、定价
- **订单管理**：处理订单、发货、退款
- **售后管理**：退换货处理
- **营销管理**：创建优惠券、促销活动

> 关键原则：每个门店的数据**完全独立**，门店 A 看不到门店 B 的数据，门店内的最大权限就是本门店的全部数据。

**为什么这样定位？**

门店是实际面向消费者的经营单元，商品定价、库存、上下架、促销等操作都需要根据本店的实际情况快速决策。如果这些操作分散在两个系统中，门店员工需要来回切换，不仅效率低，还容易造成操作遗漏。

将所有业务操作集中在门店工作台，好处有三个：第一，门店员工只需要用一个系统就能完成所有日常工作；第二，数据完全隔离保证了门店之间不会互相干扰，权限模型也变得非常简单；第三，每个门店可以根据自身情况灵活经营，不需要等总部统一操作。

## 三、核心概念：没有"总部商品"，只有"门店商品"

### 传统做法

```
总部创建商品 → 分配给门店 → 门店只能在总部商品基础上做有限调整
```

### 我们的做法

```
门店创建商品 → 可以分享给其他门店 → 每个门店独立管理自己的商品
```

所有商品都归属于某一个门店，不存在"总部商品"的概念。门店之间通过**商品分享（引用）**来实现商品流转。

如果商户需要统一管控（比如统一选品、统一品牌形象），可以创建一个**"总部门店"**，它的本质也是一个门店，只不过它的职责是创建标准商品并分享给其他门店。

## 四、商品分享机制

### 4.1 基本规则

| 规则 | 说明 |
|------|------|
| 分享即生效 | 源门店分享商品后，目标门店自动获得该商品，不需要"接受"操作 |
| 覆盖不污染 | 目标门店可以修改自己的价格、名称等，但修改只影响本门店，不会影响源商品 |
| 源头有否决权 | 源门店可以将商品设为"不可售"，所有引用该商品的门店立即生效，门店无法覆盖 |

### 4.2 门店可覆盖字段

哪些字段允许引用门店覆盖，**由源门店在创建商品时决定**。源门店可以逐个字段勾选是否允许其他门店自定义，这个配置跟随商品本身，不同商品可以有不同的覆盖策略。

例如：品牌商品可能只允许门店改价格，不允许改名称和图片（保持品牌一致性）；而通用商品可以放开所有字段让门店自由调整。

| 字段 | 默认行为 | 门店能否覆盖 | 是否由源门店控制 |
|------|---------|-------------|----------------|
| 商品名称 | 跟随源商品 | 可以覆盖 | 是，源门店可禁止覆盖 |
| 商品图片 | 跟随源商品 | 可以覆盖 | 是，源门店可禁止覆盖 |
| 商品属性 | 跟随源商品 | 可以覆盖 | 是，源门店可禁止覆盖 |
| 价格 | 门店自定 | 门店自主控制 | 是，源门店可禁止覆盖 |
| 库存 | 门店自定 | 门店自主控制 | 门店始终自主控制 |
| 上下架状态 | 门店自定 | 门店自主控制 | 门店始终自主控制（受可售状态约束） |

### 4.3 上下架与可售状态（三层控制）

这是最关键的设计，分三层理解：

```
第一层：可售状态（源门店控制）
  → 源门店可以把商品设为"不可售"
  → 一旦不可售，所有引用门店都不能卖，门店无法覆盖
  → 相当于"总开关"

第二层：上下架状态（源门店控制）
  → 源门店设置的默认上下架状态
  → 门店如果没有自己设置，就跟随这个状态

第三层：本地上下架（引用门店控制）
  → 门店可以自主决定在本店是否上架
  → 优先级高于源门店的上下架状态
  → 但无法绕过"不可售"
```

最终商品是否展示给消费者 = **可售（源门店）** AND **本地上下架（门店自主）**

> 举例：源门店分享了一个商品并设为"上架"。门店 A 觉得这个品不适合自己，可以在本店下架。但如果源门店发现这个商品有质量问题，直接设为"不可售"，所有门店立刻无法销售。

## 五、门店自建商品

门店不仅可以引用其他门店分享的商品，也可以自己创建商品。

### 审批流程（后期规划）

> 注意：审批流程在第一期暂不上线，后续根据业务需要逐步完善。

初步设想的流程如下：

```
门店创建商品 → 提交审核 → 商户后台审批 → 审批通过 → 可上架销售
```

审批逻辑的具体设计（例如哪些商品需要审批、审批层级如何设置等）需要进一步研究，确保在管控和效率之间找到合理的平衡点。

第一期门店自建商品将直接上架，不经过审批流程。

## 六、数据隔离原则

### 门店与门店之间

- 完全隔离，门店 A 看不到门店 B 的任何数据
- 门店内的最大数据权限就是"本门店全部数据"
- 唯一的跨门店数据流动通道是**商品分享（引用）**

### 商户后台

- 可以聚合查看所有门店的数据（只读）
- 可以审批门店自建商品（写审批状态）
- 不能直接修改任何门店的商品、订单、营销数据

---

## 七、角色与权限

### 商户后台角色

| 角色 | 能力 |
|------|------|
| 商户管理员 | 查看所有门店数据、管理门店、审批商品、管理商户级权限 |

### 门店工作台角色

| 角色 | 能力 |
|------|------|
| 店长 | 本门店全部功能 |
| 运营 | 商品管理、营销管理 |
| 收银 | 订单管理 |
| 店员 | 基础操作 |

### 区域运营（管多个门店的人）

区域运营需要管理多个门店的商品和营销，操作方式是**切换门店身份**：

- 在门店工作台的导航栏切换当前门店
- 每次操作一个门店的数据
- 后续可优化为"区域视角 + 门店筛选器"，在同一个页面切换门店，不需要重新登录

---

## 八、营销活动的分享

营销活动（优惠券等）的分享逻辑与商品类似：

- 源门店创建营销活动 → 分享给目标门店
- 目标门店可以调整本店的参与方式
- 跨店券的核销、预算等规则需要在后续详细设计

## 十、总结

| 原则 | 说明 |
|------|------|
| 两个系统能力分开 | 商户管"看"和"准入"，门店管"做" |
| 门店数据完全隔离 | 门店之间互不可见，商品分享是唯一的数据流通通道 |
| 没有"总部商品" | 所有商品归属门店，需要管控时通过"总部门店"分享 |
| 引用而非副本 | 分享的商品保持关联，源头信息更新会同步，门店可覆盖但不污染源数据 |
| 源头有否决权 | 源门店可以通过"不可售"一键停售所有引用门店的商品 |
| 门店有自主权 | 门店可以自主定价、自主上下架，在可售范围内自由经营 |
